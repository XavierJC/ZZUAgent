# EduAgent Phase 5：双工作区架构、课程发布与个性化教学闭环整合

## 一、项目背景

EduAgent（智学郑大）目前已经完成多个阶段的开发，具备：

- FastAPI + Vue 3 + SQLite
- LangGraph / DeepSeek 智能体
- BKT 贝叶斯知识追踪与正式评分
- 自评、学情对照及个性化学习指南
- 课程与个人 RAG
- PDF/PPTX/图片等课程资料解析
- 课程知识体系构建
- 个人笔记管理
- 原题提取、人工审核、个人题库及普通练习
- 来源选择、引用回溯、历史恢复和版本管理

根据此前交付记录，最近一次验证为552项后端测试、149项前端测试和98组隔离HTTP验证通过，数据库报告为schema10、36张表。

以上为此前记录，实施前必须重新核对实际源码和数据库，不得将历史测试结果当作本轮已验证结果。

目前项目存在一个核心产品问题：

**学习、问答、课件上传、知识体系编辑和习题审核等功能处于多个平级入口，课程内容准备与学生实际学习混杂，导致教学主线不够突出。**

本阶段不推翻现有架构，而是在原有能力上完成产品流程重组。

## 二、Phase 5 总体目标

将 EduAgent 整合为两个工作区：

### A. 学生学习端（Learning Workspace）

负责：

1. 选择已发布课程。
2. 确定学习目标。
3. 进行初始诊断。
4. 查看BKT、自评和学情分析。
5. 获取个性化学习建议。
6. 接受基于课程知识的Agent讲解。
7. 进行正式练习或复测。
8. 查看掌握状态变化与下一步计划。

学生端应以“下一步学习任务”为中心，而不是以工具菜单为中心。

### B. 课程构建后台（Course Builder Workspace）

负责：

1. 上传和管理教材、教师课件及习题资料。
2. 查看PDF/PPTX/图片解析结果。
3. 构建和审核课程知识体系。
4. 提取并审核习题。
5. 关联知识点、答案及来源。
6. 管理正式诊断候选题。
7. 检查课程内容完整性。
8. 审核并发布课程版本。

两个工作区共享现有后端服务和数据库，不新建独立项目。

本阶段的“构建后台”只是本地受控环境中的内容维护工作区，不代表已经实现教师账号、角色认证或真正的权限隔离。

# 三、Phase 5A：双工作区分离

## 3.1 前端导航调整

将原先的多个平级入口重组为：

### 学生学习端

主要入口：

- 我的学习
- 学情与目标
- AI伴学
- 学习记录

个人笔记、课程资料查看、普通练习与错题功能作为学习过程中的辅助入口保留。

### 课程构建后台

主要入口：

- 课程概览
- 课程资料
- 知识体系
- 习题管理
- 课程审核与发布

尽可能复用现有Vue页面与组件。

不要简单复制现有页面来创建两套独立功能。

对于原有URL和导航状态，提供兼容重定向或保留必要入口，避免历史链接和浏览器刷新失效。

## 3.2 首页设计

建议用户进入EduAgent后，默认看到学生学习入口。

首页主要展示：

- 当前课程
- 当前学习目标
- 最近学习状态
- 下一步建议
- 开始或继续学习
- 课程构建入口

如果用户没有选择课程或尚无有效诊断证据，应展示明确的引导，不得凭BKT先验制造薄弱知识结论。

## 3.3 保留原有功能

不得删除：

- 笔记编辑与导入
- 课程资料管理
- PDF/PPTX解析
- 原题提取与审核
- 个人题库
- 普通练习
- 课程知识体系
- RAG问答
- 学习指南

这些模块只是调整归属和使用入口。

需要保证从学生端依然能够访问个人笔记及已授权的个人学习资源。

# 四、Phase 5B：课程内容审核与发布机制

## 4.1 设计目标

建立明确的课程生命周期：

**课程草稿 → 内容审核 → 发布版本 → 学生学习。**

课程发布版本应指向一组可追溯、可验证的内容，而不是仅修改一个状态字段。

## 4.2 课程发布内容

每个课程发布版本应尽可能记录：

- course_id
- release_id
- release_version
- 发布状态与时间
- 课程知识体系版本
- 参与正式诊断的知识点配置
- 正式题目版本集合
- 评分规则版本
- 课程资料及其版本引用
- 课件检索范围
- 其他必要的内容指纹

实际数据模型以现有系统为准。

原始PDF和课件不需要因发布而重复存储。

应通过稳定来源ID、版本与内容指纹进行引用。

## 4.3 内容审核

发布前检查：

1. 知识体系是否已确认。
2. 正式知识点配置是否有效。
3. 正式题目是否具备可信答案和评分规则。
4. 题目与知识点关联是否有效。
5. 引用的资料版本是否存在。
6. 检索来源是否处于允许状态。
7. 是否有必要的学习目标和教学规则。
8. 是否存在阻止正式使用的内容问题。

不要把“人工审核答案正确”误认为“BKT模型参数已经完成统计标定”。

对于未满足正式诊断条件的内容，应明确保留为草稿或普通练习。

## 4.4 兼容现有题库

当前运行仍以原5个正式知识点和10道演示题为基础。

已有40道候选题尚未完成正式人工审核，不得自动启用。

请核实候选40题与原10题的包含关系，避免重复计算题目数量。

如果现有演示课程未达到正式发布标准，应允许保留明确标注的演示版本，但不能伪装成已完成人工审核的正式课程。

个人上传的普通练习题不得因课程发布而自动进入BKT诊断。

## 4.5 发布版本与历史兼容

必须满足：

- 已发布内容不能被后台编辑静默修改。
- 新版本需要显式发布。
- 学习会话记录所使用的课程发布版本。
- 题目修改后旧作答仍保留当时的题目及答案依据。
- 已保存的BKT、正式评分与学习历史不能因重新发布课程而变化。
- 旧课程发布版本能够被历史记录引用。
- 内容删除或失效时，历史记录应保留必要快照并标记当前状态。

若现有历史记录尚无release_id，需要设计兼容方案，不能假定它们使用某个新发布版本。

# 五、Phase 5C：个性化教学主流程

## 5.1 总体目标

将现有分散的学习模块连接成一条明确的教学路径：

**选择学习目标 → 初始诊断 → 学情分析 → 个性化学习建议 → Agent讲解 → 练习验证 → BKT更新 → 重新规划。**

这条流程应成为学生学习端的主要使用方式。

## 5.2 学习目标

学生进入已发布的课程后，选择希望学习的正式知识点或教学目标。

保留已有先修规则。

如果目标目前没有正式诊断题或未配置BKT，应明确告知，不自动生成掌握概率。

## 5.3 初始诊断

调用现有正式题目分配与评分服务。

要求：

- 诊断题来自当前允许的正式题库。
- 客观评分由确定性程序执行。
- 正式BKT更新仍遵循原业务规则。
- 不能由LLM直接赋予掌握概率。
- 没有足够测评证据时显示“待诊断”。

## 5.4 学情与路径展示

诊断完成后展示：

- 目标知识点
- 当前BKT状态
- 正式答题次数
- 最近答题结果
- 自评及信心
- 已知先修限制
- 规则生成的下一步学习建议

应明确区分：

- 客观测评事实
- BKT模型估计
- 学生主观自评
- Agent解释与建议

学习路径优先采用现有确定性策略。

不得让模型自由改写正式BKT状态、评分结果或教学先修限制。

## 5.5 Agent讲解

学生需要补充知识时，可以进入AI伴学。

讲解应使用：

- 当前学习目标
- 已确认的知识点
- 当前学情摘要
- 已发布或明确选择的课程资料
- 经授权的个人笔记

优先复用现有RAG和LangGraph流程。

模型可以辅助解释知识、给出例子或启发式追问。

必须区分：

- 有检索资料支持的内容
- 模型自身知识补充
- 当前资料不足的情况

引用必须能够定位真实来源。

教师课件如果尚未实际接入RAG，不能宣称已经实现自动课件定位；可以先通过已确认的课件位置或已有课程检索提供讲解，并把课件RAG扩展保留为独立任务。

个人笔记继续遵守逐轮外发同意。

## 5.6 练习与复测

讲解后提供明确的下一步学习行动。

例如：

- 继续阅读相关知识
- 查看课程例题
- 完成已有正式诊断题
- 进入普通练习
- 返回学情分析

正式诊断与普通练习必须区分。

只有符合当前正式评分规则的作答才能更新BKT。

普通练习可以保存历史及反馈，但不修改正式掌握状态。

完成正式复测后重新读取客观学情并计算下一步建议。

不得仅为了展示“进步”而人工调整概率或固定路径。

## 5.7 Agent作用边界

本阶段重点是整合已有Agent能力，而不是强制开发多个Agent。

Agent应承担：

- 理解学生当前学习需求。
- 在允许范围内选择教学辅助工具。
- 调用课程检索与讲解服务。
- 结合已有规则建议解释下一步行动。
- 根据新的学习证据开展下一轮辅助教学。

确定性服务继续负责：

- 正式评分
- BKT更新
- 正式题目分配
- 课程发布有效性
- 先修约束
- 数据权限与版本检查

没有必要为表现“智能”而放开模型写数据库或修改评分事实的能力。

# 六、前端体验要求

坚持现有蓝白简洁风格。

重点改善流程连贯性：

1. 从诊断结果能够直接进入建议的讲解。
2. 讲解页面能看到当前学习目标与依据。
3. 讲解结束能够直接进入适合的练习入口。
4. 完成正式练习能够返回更新后的学情。
5. 刷新能够恢复已有会话和步骤。
6. 浏览器前进后退不会重复提交题目。
7. 不因普通页面刷新意外调用下一题分配接口。
8. 窄屏界面不出现内容遮挡。
9. Markdown、LaTeX、代码和引用抽屉正常。
10. 键盘操作、焦点恢复和错误提示可用。

不得以静态演示步骤取代真实服务调用。

# 七、数据库、兼容性与安全

本次优先复用现有表及业务接口。

不要因为两个工作区分离而重新构建一套数据库。

如确需新增课程发布相关数据结构：

1. 核对真实schema。
2. 备份现库。
3. 记录所有既有表的数据摘要。
4. 使用事务进行迁移。
5. 验证完整性和外键。
6. 验证旧版本代码兼容边界。
7. 验证恢复副本。
8. 保留已有学习事实、笔记、题库和原文件。

对不同来源继续保持学生作用域和课程归属检查。

当前student_id仍是演示标识，不能仅凭前端工作区区分当作教师与学生的真实权限控制。

如果未来需要真实教师后台，需要单独开发身份认证和RBAC权限管理。

不得在没有认证的情况下将该系统作为公共多用户服务发布。

# 八、阶段验收

## A. 双工作区

- 学生学习端与课程构建后台入口明确分离。
- 原有资料上传、笔记和习题管理仍可使用。
- 旧页面链接和历史恢复正常。
- 工作区切换不会污染学习状态。
- 不出现需要学生先完成后台操作才能使用已发布示范课程的情况。

## B. 课程发布

- 草稿内容不能未经确认进入正式课程。
- 已发布版本具有稳定引用。
- 修改题目不会静默改变旧学习事实。
- 资料版本变化能被检测。
- 未审核题不能直接进入BKT。
- 已发布和演示状态明确区分。
- 重复发布和并发修改有确定处理。

## C. 教学主流程

- 学生能选择学习目标。
- 无测评证据时能够进入诊断。
- 正式作答产生正确的评分和BKT更新。
- 学情展示来源正确。
- Agent能使用允许的课程证据进行讲解。
- 讲解能够自然连接到正式练习。
- 复测后能够重新规划学习任务。
- 不同学情能够产生合理且可解释的行动差异。
- 普通练习不会改变正式BKT。
- 历史刷新不会重新调用付费模型。

## D. 回归测试

保留并验证：

- 课程与个人RAG
- 笔记管理
- 课程课件解析
- 课程知识体系
- 原题提取
- 个人题库
- 普通练习
- 自评与学习指南
- 正式评分及BKT
- 历史记录
- 数据备份与恢复

## E. 真实体验验收

进行当前环境允许的真实浏览器验收。

重点检查桌面、窄屏、键盘、完整教学流程和异常恢复。

如果浏览器自动化仍受限制，不要绕过安全限制；明确列出待负责人手动验证的步骤。

工程测试、模型质量、用户体验和真实教学效果分别报告，不得混为一谈。

# 九、实施顺序

按照下列顺序连续实施：

### Phase 5A

实施过程中先完成最小可用闭环，再逐步优化交互。

## 十二、授权边界

本轮授权完成Phase 5A～5D的正常开发、非破坏性迁移与自动化验证。

无需在每个普通编码步骤前重复征求确认。

但是以下事项必须暂停并另行确认：

- 破坏性数据库操作
